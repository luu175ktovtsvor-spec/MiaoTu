# 开发隔离与桌面发布

本机开发、打包、真包验收、更新验收和正式发布的步骤。规则总纲见 [AGENTS.md](../AGENTS.md)，版本号与包命名见[桌面版本发布与包命名](桌面版本发布与包命名.md)，Mac 签名与官网安装见 [macOS安装与发布规范](macOS安装与发布规范.md)，服务端发布见 [deploy/native/README.md](../deploy/native/README.md)。

## 改哪里、验什么

| 修改位置 | 职责 | 需要验证和交付 |
| --- | --- | --- |
| `desktop/renderer/` | 桌面界面、节点与操作 | 源码 Electron → Mac 真包 → Windows 真包 → 更新；不需要发服务端 |
| `desktop/` 宿主 | 本机项目、账号分区、任务取回、云端请求 | 桌面流程；云端协议变化时加服务端候选与旧版兼容验证 |
| `server/`、共用协议 | 云端 API；部分模块也编进桌面 `.app` | 沿调用和导入确认两端影响，目录叫 server 不代表只发服务器 |
| `web/src/landing/` | 官网 | 官网预览、媒体播放、静态发布与下载入口；通常不需要桌面打包 |
| `web/src/admin/`、管理 API | 模型开关、渠道、价格、账户 | 数据副本验收后随服务端发布 |
| `deploy/` | 运维与 systemd | 按实际组件安装验证；不因文档或 unit 修订重打桌面包 |

桌面启动的是本机 runtime 和画布，项目、媒体、会话保存在本机 workspace；云端提供登录、模型目录、报价、提交、账单与任务结果。豆包/Dola 是本机 Session 路径，要用独立分区和真实页面验证，服务端健康不能代替。

## 本机源码开发

首次或 lockfile 变化时在仓库根执行 `npm run setup`（不拉取整套公开素材）。Node 最低 22.19，云端打包用 Node 24。

开始前核对 Git 改动、正在运行的正式 App、本轮进程和端口，不覆盖其他工作的修改。每次验收建立独立目录：

```bash
cd /Users/cch/Developer/miaoimg/main
task_root=$(mktemp -d /Users/cch/Developer/miaoimg/本地资料/开发记录/desktop-dev-XXXXXXXX)
MIAO_DESKTOP_USER_DATA_DIR="$task_root/profile" \
MIAO_DESKTOP_DATA_DIR="$task_root/workspace" \
MIAO_DESKTOP_DISABLE_UPDATES=1 \
MIAO_DESKTOP_NO_GENERATION=1 \
MIAO_ALLOW_INSECURE_CLOUD_ORIGIN=1 \
MIAO_CLOUD_ORIGIN=http://127.0.0.1:9 \
npm run dev
```

这个示例故意用不可达的云端地址，只检查启动和不依赖云端的行为；登录、目录和在线任务失败是预期。需要在线能力时，先在服务器起候选（见 deploy/native/README.md「发布」第 5 步）并建立 SSH 隧道，再把 `MIAO_CLOUD_ORIGIN` 换成实际可访问的回环入口。连正式 API 只用于已授权的验收账号与范围；登录、退出和会话刷新也会写服务端状态。

`npm run dev` / `npm run preview` 会重建 `desktop/.app` 再启动 Electron，`npm run build` 只重建 `.app`。同一源码目录不要同时构建多个候选，或在别人依赖同一产物时重建；先退出自己的开发实例再重建。

`npm run desktop:renderer` 只适合界面静态调试。`npm run dev:web` 会经 `web/scripts/with_api.ts` 启动服务，不是纯静态预览，运行前核对数据库路径、凭据和副作用。

## 隔离配置

| 配置 | 作用与限制 |
| --- | --- |
| `MIAO_DESKTOP_USER_DATA_DIR` | 源码版的 Electron profile；打包版不读它 |
| `--user-data-dir=<绝对路径>` | 打包版的 profile 参数，与独立 workspace 一起指定 |
| `MIAO_DESKTOP_DATA_DIR` | 本机工作区（项目、会话、平台账号数据、工具与预览），不能指向用户正式 workspace |
| `MIAO_CLOUD_ORIGIN` | 云端地址，源码与真包都读取；不设置就连正式 API，独立 profile 不会隔离云端 |
| `MIAO_ALLOW_INSECURE_CLOUD_ORIGIN=1` | 允许回环 HTTP 地址；用隧道或断网地址时必须同时设置；正式构建与用户启动不设 |
| `MIAO_DESKTOP_NO_GENERATION=1` | runtime、cloud 和本机平台宿主拦截生成；不拦邮件、支付、账号修改或任意外部工具 |
| `MIAO_DESKTOP_DISABLE_UPDATES=1` | 开发和候选验收禁用更新；专门验收更新时只对隔离旧版解除 |
| `MIAO_DESKTOP_UPDATE_FEED` | macOS 候选更新源；Windows 读安装副本内 `resources/app-update.yml`，只改这个变量不够 |
| `MIAO_DESKTOP_DISABLE_SYNC` | 业务代码不读取，不是同步隔离开关 |
| `ENABLE_MODEL_CALLS=false` | 服务端模型调用开关；不禁用其他后台任务或第三方副作用 |

不从正式 profile 复制 Cookie、平台账户分区或凭据来省略登录。需要存量项目复现时按授权最小范围准备独立副本，活动 SQLite 用在线 backup。调试端口只绑回环，使用前确认没有别人的调试实例。

改模型能力时一并检查：节点菜单、切模型旧参数清理、Agent 工具、服务端预扣前校验、上游适配、报价/结算、管理端。上游未受理、已受理、失败、结果不明必须区分，结果不明不重新 POST。

## 打包与真包验收

1. 源码 Electron 验收受影响链路后，冻结明确提交。用户可见行为变化要递增 `desktop/package.json` 版本，并在 `server/release-notes.ts` 写好该版本的更新记录。根、web、renderer 的版本各有职责，不要求同一数字。
2. 打包入口是 `.github/workflows/desktop-macos-package.yml`、`desktop-windows-package.yml`（仓库私有时的处理见[桌面版本发布与包命名](桌面版本发布与包命名.md)），也可在对应平台执行 `npm --prefix desktop run package:mac` 或 `package:windows`，产物在 `desktop/release/`，`--publish never` 不会发布更新源。推送命中 workflow paths 会自动触发打包，并可能保存临时 Release，push 不是没有外部动作。
3. Mac 任务构建 arm64/x64，但只启动与 runner 架构一致的那个；Windows 任务装到 runner 临时目录并启动。`desktop/scripts/accept-login.ts` 覆盖它实际检查的登录/重启流程并禁止真实生成，不能据此声称所有节点出片、所有架构或旧数据迁移都通过。
4. Mac 本机验收：从候选 DMG/ZIP 取出 `.app` 放到本轮独立目录，直接启动其可执行文件。不拖进 `/Applications`，不退出或替换用户在用的妙图。新 profile 不能证明存量 workspace 迁移，涉及迁移另用授权的数据副本并先备份。
5. 用已授权的验收账号，凭据只从受保护环境注入。未授权真实生成时保持拦截，记录没验到的生成组合。验证范围随修改而定：启动、登录/退出、项目保存与恢复、任务归属、切模型、菜单和报价、本机账号、媒体读取、关闭/重启。

```bash
candidate_app="$task_root/candidate/妙图.app"
MIAO_DESKTOP_DATA_DIR="$task_root/package-workspace" \
MIAO_DESKTOP_DISABLE_UPDATES=1 \
MIAO_DESKTOP_NO_GENERATION=1 \
MIAO_ALLOW_INSECURE_CLOUD_ORIGIN=1 \
MIAO_CLOUD_ORIGIN=http://127.0.0.1:9 \
"$candidate_app/Contents/MacOS/妙图" --user-data-dir="$task_root/package-profile"
```

Mac 正式包由受控打包流程执行 Developer ID 签名和 Apple 公证，发布前逐项验证 App、ZIP 内 App 与 DMG 的签名、票据和系统评估结果；不能用本机证书存在或构建成功代替成品证明。Windows 包没有代码签名，不描述为有 Windows 信誉背书。

## 更新验收与正式发布

打包、上传临时 Release、发布官网、发布 API、发布管理端、切换更新源是不同操作，一个成功不代表其他已完成。

1. **兼容先行**：共享 API 或数据库有变化时，先验证对在线旧客户端兼容，部署服务端，最后才开放依赖新接口的客户端。
2. **候选更新目录**：安装包完整上传，核对版本、大小、SHA-512。用独立旧版实例检查发现与下载：Mac 设置候选 feed；Windows 只改隔离安装副本的 `resources/app-update.yml`（参考 `.github/workflows/desktop-update-acceptance.yml`）。`desktop/scripts/accept-update.ts` 只检查到 `ready`，不点安装，不能说验证了完整替换与重启；确需验证时只操作一次性安装副本。
3. **正式发布**：验收通过后执行 `deploy/publish-desktop-updates.sh <版本>`。它先上传 staging 并核验，再逐项替换元数据（不是两个平台一次原子切换）；替换前逐文件比较已存在的版本化安装包和 blockmap，字节不同立即停止；同时上传读取线上版本的 Mac 安装脚本。脚本的发布负责人变量只是发布意图确认，不是验收证明。
4. **公网回读**：核对 `latest*.yml`、版本化下载和固定别名，再更新官网版本与更新日志（见 macOS安装与发布规范）。

没有分群更新或灰度平台，正式 `latest*.yml` 会影响所有读取它的用户。候选没通过不改正式元数据；发布后版本不得倒退，需要修复就发更高版本。

## 记录与收尾

每次的生产状态和验收事实写到仓库外 `本地资料/开发记录/`：修改范围、提交、候选/正式版本、实际验收的平台架构与链路、未验证项、部署组件、恢复方式、清理结果。

结束时只停止本轮的 Electron、隧道、静态服务和候选进程；先停依赖产物的进程，再删临时 profile、输出、构建目录和无引用候选包；正式下载确认完整后再清本地副本。

持续增加的有效媒体和安装包也会占满磁盘：接近空间下限时暂停新构建，评估扩容或有索引的存储迁移，不能靠删用户素材维持发布。
