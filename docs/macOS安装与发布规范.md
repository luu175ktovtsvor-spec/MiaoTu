# macOS 安装、官网下载与历史版本

约束 Mac 安装包、官网下载与安装说明、更新日志、安装脚本和更新源。本机源码运行成功不能代替普通用户首次安装成功。

## 分发方式

- 现有安装包的信任状态以实际包为准；办理证书或配置公证凭据，不会改变已经生成或发布的包。正式签名包继续通过 GitHub Actions 构建，必须同时完成 Developer ID 签名、Apple 公证和成品验证。
- 尚未配置正式签名的构建保留 ad-hoc 完整性签名，不为“无签名”而剥离它。ad-hoc 签名和 `codesign --verify` 通过都不代表 Gatekeeper 接受或已公证。
- 签名、公证与普通首次安装结果如实写入发布验收记录；只有验收通过才更新正式下载。官网不展示签名状态解释、首次打开教程、系统安全设置步骤或安装脚本帮助。通过辅助路径启动不能说成双击免拦截。
- 禁止让用户全局关闭 Gatekeeper、修改系统安全策略或递归清理整个 Applications 的属性；辅助脚本只处理已校验的妙图应用副本。
- “Apple 无法验证”与“已损坏 / 包含恶意软件 / 签名完整性失败”分开处理，后者先检查文件与签名，不当作普通首次打开提示放行。
- 正式签名需要 Developer Program 会员、G2 链的 Developer ID Application 证书、公证成功与 stapler 票据；从明确提交重新构建，并验证 `codesign --verify --deep --strict`、证书链/Team ID、`spctl --assess --type execute`、公证 Accepted、`stapler validate`，在干净 Mac 上验证浏览器下载后首次打开。

## GitHub Actions 签名与公证准备

Mac 正式包仍由 `.github/workflows/desktop-macos-package.yml` 构建，不改成本机发布。签名准备不代表已经接通 CI，更不代表安装包已经公证或发布。

当前准备状态：Developer ID Application 的 G2 证书及配套私钥已具备；本机已验证代码签名、Apple 时间戳及严格签名校验，公证专用密码也已通过 `notarytool` 账号验证。本机凭据资料位于源码仓库上一级的 `本地资料/私有配置/Apple签名/`，具体账号、证书指纹、有效期、私钥和恢复方法见其中的 `苹果签名与私钥.md`；这些私密资料不纳入 Git。

正式 Mac 工作流通过专用签名脚本强制覆盖 `mac.identity`、`mac.notarize` 与 `forceCodeSigning`，精确选择 G2 证书，并在缺少凭据或验证失败时停止。`desktop/package.json` 的本地默认配置不作为正式签名证明；只认对应提交所生成安装包的实际签名、公证和系统评估结果。

Mac 打包凭据放在仅供 Mac 任务使用的受保护 Actions Environment `macos-signing`，只允许发布分支 `ChineseMain` 使用。上传私钥和公证密码时核对目标为本项目仓库，不把凭据传给其他任务或第三方仓库。

| Secret | 内容 |
| --- | --- |
| `CSC_LINK` | 包含 G2 证书与私钥的 `.p12` 文件的 Base64 内容 |
| `CSC_KEY_PASSWORD` | `.p12` 的备份密码 |
| `APPLE_ID` | 对应开发者账号 |
| `APPLE_TEAM_ID` | 对应开发者 Team ID |
| `APPLE_APP_SPECIFIC_PASSWORD` | Apple 账户生成的公证专用密码；不能用自行设置的备份密码代替 |

工作流按以下顺序处理：

1. 在安装依赖前检查必要配置；从 `.p12` 的公钥证书核对签发者为 G2、Team ID 和有效期，得到本次证书的精确签名指纹。缺少配置或验证失败就停止，不回退成临时签名。禁止把私钥或密码打印到日志。
2. 签名和公证凭据只传入需要它们的步骤；使用独立临时钥匙串导入 G2 私钥，任务结束清理。通过构建参数明确覆盖 `mac.identity`、`mac.notarize` 和 `forceCodeSigning`，不能只依赖自动发现，避免选中旧链同名证书。
3. 保留现有 arm64、x64 两套 DMG/ZIP 构建和匹配架构的实际应用验收。先对 App 完成签名、公证和票据附加，再生成 ZIP；分别验证两个 App 和 ZIP 内的 App 的签名身份、架构与票据。
4. DMG 也要签名、提交公证并附加票据，验证 `spctl --assess --type open --context context:primary-signature` 和 `stapler validate`。不能把 App 的公证结果直接当作 DMG 已有票据。
5. 给 DMG 附加票据会改变文件字节，必须在最终字节确定后重新生成相应 blockmap，更新 `latest-mac.yml` 的 SHA-512 和大小，并运行现有更新元数据核对；不能沿用附加票据前的值。
6. 仅在签名、公证、元数据和原生验收都通过后，把候选包保存到临时 Release。失败时保留脱敏诊断，不把失败包作为可发布产物。
7. 取回候选包后，仍须按既定发布顺序完成用户 Mac、Windows、更新发现和下载验收，之后才切换正式更新源。Apple 凭据只用于 Mac 任务，不能用于 Windows 代码签名。

G2 证书链的官方说明：<https://developer.apple.com/help/account/certificates/replace-developer-id-certificates>。

## Mac 验收的两条链路

1. **功能验收**：明确提交的安装包，用独立 profile/workspace 验证启动和受影响功能，保留用户现有应用、项目和登录状态。
2. **分发验收**：从官网用浏览器下载当前正式 DMG，记录系统版本、下载隔离属性、镜像内实际版本/架构和签名状态，验证 Finder 首次安装/打开。curl 下载、直接运行二进制、手动清除隔离属性后启动，都不能代替。

两个 Mac 架构分别记录实际运行范围，一个架构构建成功不等于另一个真机验证。

## 官网、更新日志与安装脚本

- 正式版本以服务器 `latest.yml` 和 `latest-mac.yml` 为准，两者必须一致。源码 package.json、候选包和更新记录条目都不能单独证明已发布。
- 官网从两个正式更新源读取版本，版本化下载和“最新”标签跟随实际发布版本；更新日志复用 `server/release-notes.ts`，只列不高于正式版本的记录；读取失败明确提示，不把候选版或过期页面标成最新。
- `deploy/install-mac.sh` 不写死版本：运行时读取正式 Mac 元数据，按真实芯片（含 Rosetta）选择，验证文件大小/SHA-512、应用标识、镜像内版本、架构和签名完整性；验证失败不覆盖原应用。
- 从 3.2.1 起，安装脚本还必须核对正式签名团队、App 与 DMG 的 Apple 公证票据和系统评估，保留下载隔离属性；旧版未公证包的兼容处理不适用于正式签名包。版本号只用于选择必须执行的校验，不能代替校验结果。
- 安装脚本不自动降级，不覆盖正在运行的目标应用，不改用户数据；复制和验证成功前保留原应用，替换失败要恢复；临时下载、挂载和 staging 退出时回收。
- `--verify-only` 只下载检查不安装；`--destination <绝对路径> --no-launch` 用于隔离安装验收，验收不得覆盖用户当前应用。
- 每次发布更新包时同步上传安装脚本（`deploy/publish-desktop-updates.sh` 会一起上传）。更新包发布后必须回读官网版本、更新日志和外置安装脚本；不在官网下载区增加安装教程。

## 是否重新打包

- 只改官网、外置安装脚本或运维文档：单独发布，不重打桌面包。
- 改应用内容、DMG 内辅助程序、签名或重新封装 DMG/ZIP：包字节变化，必须递增版本并重新计算全部元数据；不得同名覆盖已发安装包或只给旧包改名。
- 没有证书时不反复重打未公证包并声称解决了系统信任问题。

## 历史版本与收尾

- 更新日志保留真实历史，撤销的候选不混入。旧版保留必要的服务兼容，不因清文件破坏取回或账号数据。
- 服务器保留当前正式版和上一份完整、可恢复的正式包，版本化文件和固定兼容别名分清；没核实文件完整性前不按版本号推断“上一版”。
- 清理前核对 latest 元数据、版本化/固定下载链接、安装脚本、断点续传和归档引用。没有明确授权不批量删除正式历史 Release、旧版用户数据或用户当前应用。
- 临时构建/验收 Release 与 tag、废弃候选、下载包和解压目录在取回必要的脱敏证据后清理；恢复仓库私有，停止本轮进程和隧道，卸载自己挂载的镜像。
