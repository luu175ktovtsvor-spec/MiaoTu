# 模型成本与积分（内部资料）

## 穗禾采购成本切换（2026-10-25）

当前客户请求链路为：`客户端 → 妙图服务端 → 穗禾 API → 火山引擎资源`。旧火山/秘塔通道和历史任务保留在内部，历史任务按任务创建时保存的 `provider` 查询和结算。

2026-10-26 用户确认加价单位：**0.5 分钱 = 0.005 元**。仅穗禾新请求：图片售价为逐张采购成本 + 0.005 元/张；视频先按火山 token 公式 × 采购折扣预估，成功后优先采用上游明确确认的人民币成本，再加输出时长 × 0.005 元/秒。报价、预扣和退款保留四位小数，与现有四位小数余额账本一致，不按 0.1 或 0.01 积分进位。已有任务冻结原加价，不重算历史；其他渠道价格保持原规则。例：Seedream 4.0 2K 成本 0.40，客户价 0.405；4 秒视频加价合计 0.02 元。该差价尚未扣支付手续费、服务器费用及其他成本，不能称为净利。

穗禾是火山资源的采购渠道；给出的 Seedance 成本按“火山官方 token 价 × 穗禾采购折扣”计算：Seedance 2.5、2.0 使用 0.81；2.0 Fast、Mini 使用 0.60。这是我们的内部采购成本，不是对客户再打一次折，也不是把穗禾返回的数值直接当人民币。计算输入视频档位、分辨率、比例、24 FPS、最低 token 规则和实际返回的 `completion_tokens`，折扣只应用一次。穗禾任务的 `estimated_cost` / `actual_cost` 原始单位尚未得到供应商确认，保存在上游留档中，不能直接当人民币。

2026-10-26 真实任务新增返回 `billing.status=confirmed` 与 `billing.charged_cny`。该字段明确是人民币，因此结算直接采用它，**不再乘一次折扣**。`super_economy` 实测为低清生成再增强，账单包含生成费用和增强费用，不能拿目标 720p 像素估算值当最终实扣。无确认账单时仍保留公式预估或实际 token 口径，并标明依据。预扣额继续作为客户上限，超额成本记录到管理端差额，不追加扣成负余额。原生视频预估计入实测多出的边界帧，减少低估。

示例：Seedance 2.0、480p、16:9、4 秒、无参考视频，飞书公式得 40,176 token；官方 46 元/百万 token = 1.848096 元，采购成本为 `1.848096 × 0.81 = 1.49695776` 元，记录为 1.497 元。含参考视频时使用 28 元/百万 token 档；1080p 使用 51/31；4K 使用 26/16。Fast 使用 37/22 元/百万 token，Mini 使用 23/14 元/百万 token，再乘 0.60。

报价图中的“元/秒”仅作供应商示例，未证明它覆盖所有比例、声音、参考素材和创作档，不能取代 token 公式。图片按穗禾确认的逐张成本：Seedream 4.0（1K/2K 0.40）、4.5（2K 0.45）、5.0 Lite（2K/3K 0.42）、5.0 Pro（1K 0.60、1.5K 0.85、2K 1.20）。未给出成本的 4K 图片暂不向客户开放，避免后台报价虚构。

## 请求转发记录

穗禾通道使用服务端 `SUIHE_API_KEY` 和 `SUIHE_BASE_URL`（默认 `https://api.suihemedia.cloud`），Key 不进入前端、安装包或上游调用日志。新任务先按穗禾 `GET /v1/models` 的 `request_model` 映射模型，再提交到 `/v1/images/generations` 或 `/v1/videos/generations`；所有结果按 `task_id` 轮询 `/v1/tasks/{task_id}`。

火山侧的提示词、比例、时长、分辨率、声音、种子、首尾帧和参考素材仍从同一份服务端规范进入请求。无参考图/视频时使用 JSON；图片参考使用穗禾 `images` multipart 字段；视频参考使用穗禾的 `function_mode`、`image_file_N`、`video_file_N`、`audio_file_N` 字段，并在 multipart 中把分辨率发送为 `video_resolution`。旧火山、秘塔任务继续按任务保存的 `provider` 查询和结算，不能因当前目录切换而改路由。

> 只给服务端和管理端使用。公开接口、画布和节点只出现积分：不出现供应商名称、
> 不出现美元/人民币单价、不出现渠道倍率。

## 后台图片覆盖价格

`settings.prices[模型ID].image` 可设置统一单价，或按尺寸设置单价并用 `default` 保留其余尺寸的单价。统一数字切换为非空尺寸表时，旧数字自动保留为 `default`；只修改一个尺寸不会重置其他尺寸或自定义尺寸的原单价。显式空表 `{}` 清空该模型的图片覆盖价，重新设置数字则统一覆盖全部尺寸。没有配置 `default` 时，未覆盖尺寸继续使用原定价规则。

模型目录、管理端价目和新请求报价使用同一有效价格；报价尺寸表携带已配置的 `default`。图片任务仍按创建时的预扣金额及实际保存张数结算，后续调价不重算旧任务。

## 积分口径

- 1 积分 = 1 元（充值 100 分 = 100 元）。
- 图片（用户 2026-10-06 定）：GPT 图片 0.2 积分/张、Grok 图片 0.1 积分/张、豆包 Seedream = 官方原价 + 0.15 积分/张（5.0 Pro 按 ≤261 万 / >261 万像素分两档）。积分保留两位小数。
- 视频：创建前按模型、分辨率、模式、声音和输入媒体做安全预扣；成功后优先按上游返回的实际 usage 或套餐用量对账，非Grok向上取整到0.01、最低0.01积分，Grok保持原有规则；失败自动退回。不能把所有视频通道统一当成单纯秒价。
- 文本模型暂不对用户收费。

| 秘塔 H3 / Seedance | 秘塔自家积分：时长 × 分辨率积分/秒 + 输入视频秒数 × 同档积分/秒 + 图片超额 5.7 积分/张 + H3 Context IR 5.7 积分/次，再 × 0.0108 元/积分（最贵可购档位） | `metaso_credits_most_expensive_tier`（Seedance 两档标注 `_unverified`，因为官方没有公开价目） |

每次生成成功后，`generations.upstream_cost` 会写入这条成本（JSON：`rmb` + `basis` + `detail`）。管理端对账视图（`reconciliation()`）会给出：

- `upstreamCostRmb`：全部生成的上游成本合计；
- `chargedPoints` / `marginRmb`：用户实际扣分（1 积分 = 1 元）与毛利，`marginRmb = chargedPoints - upstreamCostRmb`；
- `missingCostRows`：还没记录成本的记录数（历史数据）。

成本只出现在管理端接口，公开配置和画布都看不到（`configured`、能力、积分之外不返回任何成本字段）。

## 上游留档机制（2026-10-06 新增，用户要求）

目的：不用花钱去试探，**让真实用户的使用自己把数据攒起来**，之后从库里反推每个档位的真实单价（包括上游没公开价的档位）。

每次生成都会在 `upstream_calls` 表留一条：

| 字段 | 内容 |
| --- | --- |
| `request` | 我们实际发出去的东西（路径 + body，密钥类字段从来不在里面） |
| `response` | 上游原始返回（脱敏前原样存，最多 40KB） |
| `usage` | 上游给的计费用量（秘塔 `output_seconds`/`input_seconds`/`input_image_count`；火山 `completion_tokens`） |
| `cost_rmb` / `cost_basis` | 我们按档位算出来的成本与口径标记 |
| `credits_before` / `credits_after` / `credits_delta` | **秘塔专属**：提交前后各读一次它的账户余额，差额就是这一单实际扣掉的积分 |
| `tier` / `seconds` / `has_input_video` | 这一次请求落在哪个档位、多少秒、有没有输入视频 |
| `status` / `error` | `ok` / `failed` 与失败原因 |

查询入口（管理员）：
