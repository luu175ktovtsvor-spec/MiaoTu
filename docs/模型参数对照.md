# 模型参数对照（内部核对记录）

## 穗禾客户通道（2026-10-25）

Seedance 2.5、2.0、2.0 Fast、2.0 Mini 以及 Seedream 4.0、4.5、5.0 Lite、5.0 Pro 的客户请求统一走服务端穗禾通道；旧通道仅用于历史任务、内部保留和回溯。服务端实时读取 `GET /v1/models` 的 `request_model` 与能力，客户端不接触穗禾 Key。

穗禾图片和视频都是异步任务：提交后只保存响应里的 `task_id`，轮询 `GET /v1/tasks/{task_id}`；响应中的 `id` 不能替代 `task_id`。图片参考素材优先 multipart 原文件，视频 2.5 的参考素材使用 `image_file_N`、`video_file_N`、`audio_file_N`。客户目录按图片/视频分类，每个模型继续有独立开关和售价；管理端同时显示当前客户通道、历史通道、配置状态和采购成本来源。

## 管理端渠道开关（2026-10-25）

管理端模型目录按“一个客户端模型一行”展示四类信息：客户端模型 ID、当前上游、上游模型 ID、渠道配置与开关。渠道开关保存在 `settings.modelChannels`，例如：

```json
{
  "modelChannels": {
    "seedance-2.5": { "suihe": true, "ark": false },
    "doubao-seedream-5-0-pro": { "suihe": true, "ark": false }
  }
}
```

打开某个渠道会把它设为当前路由；关闭当前渠道时，若有已配置的候选渠道就自动切换，否则同时关闭该客户端模型。`settings.models[modelId]` 仍是客户端总开关。新任务在预扣前再次校验当前渠道，已入队或已接受的任务保留创建时的 `provider` 快照，避免后台切换影响历史任务。

客户端 `/api/imagine/config` 只返回公开模型 ID、显示名和参数能力，不返回 `provider`、上游名称、上游模型 ID 或渠道开关；上游归属只在管理端和本内部文档中出现。

## 穗禾配置索引（内部）

- 正式 Base URL：`https://api.suihemedia.cloud`。代码只保存根地址，接口路径分别追加 `/v1/models`、`/v1/images/generations`、`/v1/videos/generations` 和 `/v1/tasks/{task_id}`。
- Key 只使用项目的密钥文件名 `secrets/suihe-api-key`，内容不写入源码；服务端通过 `SUIHE_API_KEY` 读取，字段映射见 `server/runtime-secrets.ts`。
- `SUIHE_BASE_URL` 只作为服务端地址配置。前端、安装包、Git 历史和上游留档都不能出现 Key 内容。

## 画布参考素材怎么给上游（图片/视频/音频通用）

上游只接受公网可访问的素材地址，画布文件又存在用户自己的工作区里，所以：

1. 画布把本地素材路径 `POST /api/imagine/reference-url` 交给服务端；
2. 服务端校验文件属于当前用户，签发 6 小时有效的只读链接
   `https://miaoimg.cn/api/imagine/reference?t=<token>`（token 绑定用户 + 路径 + 文件修订号 + 过期时间，
   用服务端密钥 HMAC 签名，密钥首次使用时生成并存在数据卷设置表里）；
3. 秘塔 / 火山按这个链接自己抓取素材（支持 Range），生成完自然失效；
4. 参考视频按模型要求校验：H3 单个参考视频 2–15.5 秒、画面 256–5760 像素；
   服务器用 ffprobe 读取账号工作区里的真实时长，客户端上报值不作为最终计费依据。
   音频同样读取真实时长；Seedance 参考视频/音频各自合计不超过 15 秒。
   仅探测本账号签名媒体，元信息按修订号缓存，并发上限 2；读不到时长时在扣积分前拒绝请求。

## 秘塔 MiniMax-H3（直连 MiniMax 协议）

- 来源：秘塔官方《New API 接入》页面与官方任务插件 `minimax-h3-metaso.plugin.js` v1.1.0。
- 提交：`POST https://metaso.cn/api/minimax/v2/video_generation`
  - `{ model: "MiniMax-H3", content: [...], duration, resolution, ratio }`
  - `content`：`{type:"text",text}`、`{type:"image_url",image_url:{url},role}`、
    `{type:"video_url",video_url:{url},role}`、`{type:"audio_url",audio_url:{url},role}`。
  - role：`first_frame` / `last_frame` / `reference_image` / `reference_video` / `reference_audio`。
  - `duration`：4–30 的整数；`resolution`：`480p` / `768P` / `1080p` / `2K`，其中 2K 最长 15 秒；
    `ratio`：`adaptive`、`21:9`、`16:9`、`4:3`、`1:1`、`3:4`、`9:16`。
  - `context_ir_enabled`（提示词优化 / Context IR）：秘塔默认开启、按次 5.7 积分单独计费，请求里的值优先于控制台全局开关。
    我们每次显式发送：默认 `true`；节点「高级设置 → 原样使用提示词」打开时发 `false`，预扣与结算都不再含这 5.7 积分。
  - 比例按秘塔自家页面（metaso.cn/minimax-h3）的组包规则：纯文生视频选「自适应」改发 `16:9`；
    **H3 带首尾帧照用所选比例**（7 档都可选）；参考模式原样保留 `adaptive`。旧客户端的不合规比例由服务端纠正，不拒绝。
  - 官方插件还支持 `callback_url`、`aigc_watermark`、`fast_mode`（优先通道，VIP、价格 2 倍）以及独立的
    视频再生成接口（768P → 2K，按任务 ID 需白名单）；这些当前未开放给前端。
- 查询：`GET https://metaso.cn/api/minimax/v2/query/video_generation/{task_id}`，
  task_id 是路径段，不是 `?task_id=`；返回 `body.task`，视频地址在 `task.content.url`。
- 计费要点：参考视频按输入时长 × 最终分辨率计费；图片前 5 张免费，超出 5.7 积分/张；输出超过 15 秒时按官方 `longOutputCreditPerSecond` 的 2 倍档计费。

## 秘塔 Seedance 2.0 / Mini（与 H3 共用 MiniMax 兼容协议）

- 来源：秘塔官方前端 `minimax-h3` 页面的 API 调用示例与前端源码（`studio` 页面生成的
  cURL 代码），核对日期 2026-10-05。**不是 OpenAI 兼容端口**：`/api/openai/v1/videos`
  只用于把 H3 映射成 `sora-2` 的 New API 渠道，Seedance 走统一的任务接口。
- 提交：`POST https://metaso.cn/api/minimax/v2/video_generation`
  - `{ model: "seedance-2.0" | "seedance-2.0-mini", content: [...], duration, resolution, ratio, context_ir_enabled: false }`
  - `content` 与 H3 相同：`text` / `image_url(first_frame|last_frame|reference_image)` /
    `video_url(reference_video)` / `audio_url(reference_audio)`。
  - 普通单图和混合参考一律使用 `reference_image`；只有 `startFrameOptional` /
    `endFrameOptional` / `startEndRequired` 使用 `first_frame` / `last_frame`。
  - `resolution`：Mini 支持 `480p` / `720p`；标准版支持 `480p` / `720p` / `1080p` / `4K`。
    之前误按 OpenAI 端口传 `1280x720`，官方接口会直接返回 `Seedance resolution 不支持`。
  - `ratio`：`21:9` / `16:9` / `4:3` / `1:1` / `3:4` / `9:16`；图生视频固定传 `adaptive`，
    文生视频选到 `adaptive` 时归一成 `16:9`（与官方前端一致）。
  - `duration`：4–15 的整数秒；Seedance 必须显式关闭 H3 Context IR（`context_ir_enabled:false`）。
  - 比例：带首尾帧固定 `adaptive`；纯文生视频「自适应」改发 `16:9`；参考模式可用 `adaptive`。
  - 参考上限：图片 9 张、视频 3 个、音频 3 个，视频与音频各自合计不超过 15 秒；
    声音由模型原生输出，协议没有声音开关字段。
- 查询：同 H3，`GET /api/minimax/v2/query/video_generation/{task_id}`，
  成功后从 `task.content.url` 取 mp4；该地址是带签名的 `files.metaso.cn` 链接。
- 取流：服务端统一走同源代理 `/api/imagine/video-content?requestId=...`（透传 Range，
  必要时带 Bearer Key），画布只拿到自己账号下的代理地址。
- 历史记录（2026-10-05）曾有一次 `seedance-2.0-mini` + 480p + 4 秒真实往返成功；
  本轮验收不再发送真实生成请求，改用模拟响应核对提交、轮询、取流和失败退点路径。

## 火山方舟 Seedance 2.0 Fast

- 来源：火山方舟《创建视频生成任务》API 文档（2026-09-22 更新）。
- 提交：`POST https://ark.cn-beijing.volces.com/api/v3/contents/generations/tasks`
  - `{ model, content: [...], duration, resolution, ratio, generate_audio, watermark, ... }`
  - `content` role：`first_frame`、`last_frame`、`reference_image`、`reference_video`。
  - 官方默认 `generate_audio = true`；我们**始终显式传值**（用户没开声音就传 false），
    避免用户关掉声音后仍出有声视频、多耗 token。
- 官方能力（Seedance 2.0 系列教程 2026-09-29 + 模型列表页 2026-09-28）：
  - 文字 / 首帧 / 首尾帧 / 全模态参考 / 编辑视频 / 延长视频 / 有声视频 / 返回尾帧 都支持；
  - 参考上限：图片 0–9、视频 0–3、音频 0–3，可组合（不支持纯音频、文本+音频）；
  - 比例：21:9、16:9、4:3、1:1、3:4、9:16、adaptive；Fast 分辨率 480p/720p；时长 4–15 秒；mp4；
  - 编辑 / 延长通过 `reference_video` 参考 + 提示词自动判定，没有单独端点；画布公开了编辑和延长模式，服务端仍发同一个方舟任务接口；
  - Seedance 2.5 的首帧、首尾帧、单图、编辑和延长只发 `adaptive`。Seedance 2.0 系列这些任务按用户选的比例发送。Fast 没有 1080p；带参考时也不会改发 1080p。
  - 样片模式（draft）和离线推理（flex）Seedance 2.0 系列不支持，没有开放；
  - `frames` 官方只对 Seedance 1.0 pro / pro fast 开放（取值 29–289，且必须是 25+4n）：官方《创建视频生成任务》里 `frames` 的「模型支持」只列了这两个模型。Seedance 2.0 系列只能传整数 `duration`，服务端会在预扣前拒绝旧客户端传来的 `frames`，避免把无效字段发给方舟。
- 已按官方补齐：参考图 9 / 视频 3 / 音频 3、完整比例列表、`return_last_frame`、
  `tools(web_search，仅纯文本)`；Seedance 2.0 不接受 `seed` / `camera_fixed`，服务端会在预扣前明确拒绝，而不是把错误字段发给方舟。
- 方舟任务查询的 `usage.completion_tokens`（视频接口同时返回 `total_tokens`）保留在生成记录中，并按官方 token 刊例做成功后对账；创建前仍用参数上限预扣，避免上游请求已经发出后余额不足。
  公开 ID 统一成 `seedance-2.0-fast`（旧横线写法继续兼容）。

## Grok（Yunshu API `/v1/videos/generations`）

- 线上 Yunshu 分组已经收敛：`妙图 Grok 原生通道`（组 13）是唯一 active 的 Grok 分组；历史的 `妙图 Grok 图片视频`（组 12）已软删除并停用对应 Key。妙图的 `GROK_API_KEY` 对应组 13，图片/文本使用的 `YUNSHU_API_KEY` 对应组 11。文档只记录分组标识，不记录 Key 内容。

- 请求：`POST {YUNSHU_BASE_URL 去掉结尾 /v1}/v1/videos/generations`；响应里的 `request_id` 是任务 ID，
  查询 `GET /v1/videos/{request_id}`，终态是 `done`，视频在 `video.url`。
  服务端严格使用 xAI 字段：
  - 文生 / 图生：`{ model, prompt, duration, aspect_ratio, resolution }`；
  - 单图首帧：再加 `image: { url }`；
  - 1.5 参考图：使用 `reference_images: [{ url }]`（最多 14 张）；
  - 1.5 首尾帧：使用 `image: { url }` 与 `last_frame: { url }`；
  - 1.5 关键帧：使用 `keyframes: [{ image: { url }, timestamp_s }]`，最多 4 个，时间点必须在视频内部并对齐 1/3 秒；
  - 1.5 预设声音：使用 `reference_audios: [{ voice_id }]`，最多 3 个；上传音频文件不是普通账号可用的同一参数；
  - 编辑 / 延长（**只有经典版 `grok-imagine-video`**）：分别调用 `/v1/videos/edits`、`/v1/videos/extensions`，只传官方支持的
    `video: { url }` 与提示词（延长另传 2–10 秒的 `duration`）；编辑不发送自定义时长、比例或分辨率。
    编辑按输入视频真实时长（最多 8.7 秒）计费，延长按原视频 2–15 秒输入 + 新增 2–10 秒分别计费；
    两种模式的输出格式按官方限制使用最高 720p，画布会禁用无效的比例/分辨率控件。
  - 两个 Grok 模型都显式支持 `generate_audio` 开关；用户关闭声音时请求体发送
    `generate_audio:false`，不会依赖上游默认值。
- Classic `grok-imagine-video`：支持文生、单图生视频（`image` 钉首帧）、**参考图生视频（
  `reference_images` 最多 7 张）**、编辑与延长；1–15 秒、480p/720p。**参考图模式官方最长 10 秒**；
  它**拒绝 `last_frame` / `keyframes`**，也**拒绝把 `image` 钉帧和 `reference_images` 放在同一请求里**

### 火山方舟（官方文档 + 官方价格页）

来源：《创建视频生成任务》《查询视频生成任务》《模型价格》。核对到的原文要点：

方舟 Seedance 2.5 与 2.0 Fast 的时长列表包含 `-1`（界面写「自动」，预扣按该型号最长秒数，成功后按实际用量结算）。秘塔这几条视频接口没有这条选项，不补。

实测链路（全部通过）：

| 步骤 | 结果 |
| --- | --- |
| 提交 `POST /api/imagine/video` | `202`，`status=queued`，**预扣 1 积分**（生成前就记账），余额 10 → 9 |
| 队列派发 | 4 秒后转 `running`（服务端队列 → 秘塔 `POST /api/minimax/v2/video_generation`） |

| 验收账号 | 验完停用，避免留下可用账号 |

秘塔查询接口返回的任务对象字段（实测）：

```json
{
  "id": "…", "model": "MiniMax-H3", "status": "success", "modality": "video",
  "duration": 4, "resolution": "768P", "ratio": "16:9", "task_type": "…",
  "estimated_remaining_seconds": 0, "title": "…",
  "content": { "url": "https://files.metaso.cn/…" },
  "usage": { "total_seconds": 4, "input_seconds": 0, "output_seconds": 4, "input_image_count": 0 }

```

要点：

- **秘塔会回自己的计费用量**（`output_seconds` / `total_seconds` / `input_seconds` / `input_image_count`），所以成本可以完全按上游实际用量对账，不需要我们猜；服务端现在优先用这几个字段算成本，缺字段才退回参数估算。
- 按这份用量算出的 768P 4 秒成本 = `4 × 10.2 + 5.7(Context IR) = 46.5 积分 × 0.0108 = 0.5022 元`，与秘塔 studio 默认显示的 `创建 (46.5 积分)` 完全吻合。
- 查询返回里还有 `estimated_remaining_seconds`，以后可以直接用来显示更准的等待时间。
- 状态用的是 `success`，我们已归一成内部 `succeeded`；`FAILURE`/`error` 等也会归一到 `failed`（本轮之前修过）。

### Grok 传参为什么现在判不了（2026-10-06 实测）

用四种 body 打 `/v1/videos/generations`：正常 xAI 字段、`duration` 传字符串、缺 `prompt`、空 `image` 对象——**四种都返回同一个 `503 No eligible Grok media accounts`**。结论：网关在**选账号阶段就短路了，还没有解析请求体**，所以现在既验证不了字段名是否被透传，也拿不到任何校验错误。账号 `rate_limit_reset_at = 2026-10-07 09:47 +08`，恢复后跑 `/opt/miaoimg/oip-grok-verify.sh`：

- 判据：用 classic 模型带 `last_frame`（xAI classic 官方明确不支持该字段）发最小请求（1 秒 480p）。
  - 返回 4xx 且提到 `last_frame` → **字段被透传**，我们现在的字段名是对的；
  - 返回 200 并成功生成 → **未知字段被网关丢弃**，需要按网关自己的字段名（二进制里只见 `image_url` / `video_url` 这类）改写法；
- 生成成功后用 ffprobe 看成片有没有音轨，判断 `generate_audio:false` 是否生效。

### Grok 字段问题会自己留下证据

`upstream_calls` 会把每次上游调用的**发出 body** 和**上游原始返回**原样存下来。等 Grok 账号恢复配额、第一个真实请求跑通之后，直接看那一条留档就能判定：

- `request.body` 里我们发了 `image` / `last_frame` / `keyframes` / `reference_audios` / `generate_audio`；
- `response` 里如果出现「不支持某字段」之类的报错，说明字段被透传给了 xAI；如果照常出片，说明网关把它们丢掉了，需要改成网关自己的字段名（二进制里只见 `image_url` / `video_url` 这类叫法）。

不用再额外花额度去试探。
